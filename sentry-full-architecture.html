📨 Envelope — What's inside
A single Envelope can carry:
• Error event (with stack trace, breadcrumbs, context)
• Transaction + all child spans
• Session update (start/end/crash)
• Replay recording chunk (DOM mutations)
• Log entries
• Attachments

Why Envelopes: Before Envelopes, SDKs sent individual events to /store/. Envelopes batch heterogeneous data in one request — critical for performance and offline queuing.
🛡️ Relay — The 4 things it does
1. Rate limiting — enforces org/project/DSN quotas. Returns 429 with X-Sentry-Rate-Limits + Retry-After headers. SDK backs off.

2. PII scrubbing — Advanced Data Scrubbing rules: @ip:replace, @password:remove. Sensitive data stripped before entering pipeline.

3. Event filtering — drops events matching inbound filters (browser extensions, crawlers, ignored error messages).

4. Normalization — validates schema, standardizes fields, normalizes stack trace formats.
📬 Kafka — Why it exists
Decouples ingest from processing. If processing is slow or restarting, Kafka buffers the data — nothing is lost.

Topics:
• events — errors
• transactions — spans/traces
• sessions — release health data
• attachments
• replay-recordings

Multiple consumers read independently — Snuba for storage, alerting workers for notifications, etc.

Handles spikes: Customer outage generates 10M errors/hour? Kafka absorbs it.

🔍 Symbolication — Making stack traces readable
JavaScript: Minified code → source maps (JSON) → original file + line + column
Without: a.js:1:34291
With: checkout.js:142 processPayment()

Native (iOS/Android/C++): Debug symbols (DWARF, PDB) → function names + line numbers. SymCache files for fast lookups.

Source maps are uploaded during build via sentry-cli or vite/webpack plugin, associated with a release.
🗂️ Grouping — How events become Issues
Default fingerprint: Stack trace frames (filtered to "in-app" only) + exception type + message

Custom fingerprint: setFingerprint(['auth-failure', '{{ default }}']) — forces all auth errors into one Issue

The in_app flag: Marks frames as your code vs. library code. Only in-app frames drive default grouping. Also controls "Most Relevant Frame" highlighting in the UI. Set via inAppInclude / inAppExclude.
🏷️ Enrichment — Adding context
Geo-IP: Resolve IP to country/city
Release association: Link event to the release version that was running
Tag extraction: Pull indexed tags from event data
Context merging: Combine user, browser, OS, device info
Issue linking: Match fingerprint to existing Issue or create new one

After enrichment, the fully processed event is written to storage.
Phase 5 — Storage
🗄️ ClickHouse — The Analytics Engine (via Snuba)
Stores: Raw event data, spans, logs, metrics, aggregates — everything you query and visualize.

Why ClickHouse: Columnar OLAP database. Fast aggregations over billions of rows. When you search issues, filter by tag, view a trace waterfall, check p95 latency — that's ClickHouse.

Snuba is the query layer on top. It takes search queries (SNQL/MQL), validates them, compiles to ClickHouse SQL, returns results. Powers all of Sentry's visibility features. Uses Redis for caching.

Think of it as: The observability data warehouse.
🐘 PostgreSQL — The Application Database
Stores: Organizations, projects, teams, users. Issue state (resolved, ignored, assigned). Alert rules. Integration configs. Saved searches. Django ORM app state.

Does NOT store: Raw event data (that's all ClickHouse).

ACID guarantees: Needed for transactional operations like updating issue state, managing user permissions, storing alert rules.

Think of it as: The configuration and state database.

🔔 Alerts — two types
Issue alerts: New issue, frequency > N in time window, affects > N users, regression (resolved issue reappears)

Metric alerts: p95 latency > 2s, error rate > 5%, custom metric threshold. Three modes: static, percent change, anomaly detection.

Anatomy: Condition → Filter → Threshold → Action (Slack, email, PagerDuty, Opsgenie, webhooks)
🔌 Integrations — closing the loop
GitHub: Stack trace → source linking, commit blame, suspect commits, PR comments

Jira: Sentry error → Jira ticket → status syncs back bidirectionally

Slack: Alert rules route rich notifications to channels

📈 Release Health — did the fix work?
Crash-free session rate — the key metric. 99.5%+ is healthy.

The loop: Deploy v2.1.0 → adoption tracked → crash-free drops 99.8% → 97% → regression alert fires → engineer sees resurfaced error → GitHub shows the commit → fix deployed → crash-free recovers.

That's the full circle. From user click to engineer fix, verified by release health.
The single thread that connects everything: The trace ID. Generated when the user clicks a button in the browser. Propagated via HTTP headers to every service. Attached to every Error, Span, and Log. Stored in ClickHouse. Used to pull the full picture together on the Issue Detail page. One ID, one story, end to end.
