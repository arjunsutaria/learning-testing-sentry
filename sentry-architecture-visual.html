Key frontend detail: The SDK injects sentry-trace + baggage headers into every fetch() to targets matching tracePropagationTargets. This is how the frontend trace connects to the backend trace — same trace ID, propagated via HTTP headers. Head-based sampling: the frontend decides whether to sample this trace, and the backend respects that decision.
What happens on a render crash: Component throws during render → React unmounts the tree → <Sentry.ErrorBoundary> catches it → sends Error to Sentry with component stack trace → renders fallback UI. Without the boundary: blank white screen, no Sentry event.

Distributed trace in action: The backend SDK reads sentry-trace from the inbound request and continues the same trace — creating a new span as a child of the frontend's fetch span. Same trace ID, different span IDs. This is how one user action produces a single trace spanning browser → API → DB.
What reaches Sentry vs. what doesn't:
• throw or unhandled rejection → setupExpressErrorHandler → ✅ Sentry
• res.status(404).json(...) → handled response → ❌ NOT Sentry (unless you call captureMessage)
• Promise.reject() with no await → silent failure, server returns 200 → ✅ Sentry catches via unhandledRejection

Snuba explained simply: Snuba is the query layer between the Sentry web app and ClickHouse. It takes search queries (SNQL/MQL), validates them, compiles to ClickHouse SQL, and returns results. Every time you search issues, view a graph, or check latency percentiles — that's Snuba querying ClickHouse.
Why source maps are critical: Without them, a JS stack trace shows a.js:1:34291. With them, you see checkout.js:142 processPayment(). Source maps are uploaded during build (via sentry-cli or vite/webpack plugin) and associated with a release. Symbolicator uses them during event processing to resolve every frame.
